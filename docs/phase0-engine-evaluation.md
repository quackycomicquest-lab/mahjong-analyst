# フェーズ0：AIエンジン・ルールエンジン 採用検証レポート

調査日：2026-11-05 ／ 対象仕様：[SPEC.md](SPEC.md) §4-2, §4-3, §13

> 本レポートは**公開情報（各リポジトリのREADME・LICENSE）の調査段階**。実機での推論速度・一致率の計測はまだ行っていない。

---

## 1. 結論（先に）

1. **すぐに組み込める「強い・ライセンス適合・iPhoneで動く」既存AIは存在しない。**
   - Mortal：コードは公開だが**学習済みモデルは非公開**（作者は公開予定なしと表明）。
   - Akochan：独自ライセンスで**AI部分の再配布禁止**。C++/boost製でブラウザ・iPhoneで動かす経路がない。
   - Kanachan：**学習済みモデルも学習データも非提供**。雀魂の牌譜を自力収集する前提。
2. したがって MVP の Evaluator（③）は **自前実装（TypeScript＋必要に応じWASM）** とし、
   - 牌効率・打点・和了率は**シミュレーション／探索で期待値を算出**
   - 守備（放銃リスク）は**ヒューリスティック推定**で「暫定評価」と明示
   - 将来、ニューラルモデルを差し込めるよう**評価インターフェースを固定**する
   …が現実的。仕様 §3-3「根拠のない点数を作らない」とも整合する。
3. ルールエンジン（①）は **TypeScriptで自前実装**し、既存のMIT/Apacheライブラリを**テストの正解データ生成（オラクル）**に使う。

## 2. AIエンジン候補の比較

| 観点 | Mortal | Akochan | Kanachan | NAGA等の商用サービス |
|---|---|---|---|---|
| コードのライセンス | AGPL-3.0-or-later | 独自（個人の研究・教育は無償、商用は要許諾、**AI部分の再配布禁止**） | READMEに明記なし（要確認） | 非公開 |
| 学習済みモデル | **非公開**（作者「公開予定なし」） | 探索型AIのためモデル不要 | **非提供** | — |
| 実装 | Rust（libriichi）＋Python/深層強化学習 | C++（Make, boost） | C++＋Python/PyTorch | Webサービス |
| mjai対応 | あり | あり（mjai_client等） | — | — |
| 候補ごとの期待値 | 方策/Q値ベース（要調査） | 探索で各打牌の期待値を出す設計（akochan-reviewerの基盤） | — | 牌譜解析として出力 |
| Macで動作 | 学習・推論とも可能だがモデルが無い | ビルド可能（Makefile_MacOSあり） | 学習には大規模GPU資源 | ブラウザ経由 |
| iPhone/PWAで動作 | ONNX化すれば理論上可。ただしモデルが無い | **経路なし**（移植はライセンス上も困難） | — | オフライン不可 |
| 隠し情報を使わない評価 | 設計上は可能 | 可能 | — | — |
| 本プロジェクトへの適合 | ✕（モデル入手不可） | △（Mac上で個人用の参照評価器としてのみ） | ✕ | ✕（オフライン・自動連携不可） |

### 補足
- **Mortal**：自前で学習させる道はあるが、大量の牌譜と GPU 学習が必要で、個人プロジェクトの初期段階には重すぎる。AGPL のため、改変版を公開サーバーで提供する場合はソース公開義務が生じる点にも注意。
- **Akochan**：自分のMac上でローカル実行し、自前Evaluatorの**妥当性チェック用の比較相手**に使う用途なら、個人研究の範囲に収まる可能性がある。ただしアプリへの同梱・配布はしない。利用前に LICENSE 原文を自分で確認すること。
- **Kanachan**：雀魂の牌譜収集が前提で、利用規約上のリスクもある。採用しない。

## 3. ルールエンジン候補（①）

| ライブラリ | 言語 | ライセンス | 主な機能 | 用途案 |
|---|---|---|---|---|
| [mahjong](https://github.com/MahjongRepository/mahjong)（MahjongRepository） | Python | MIT | 翻・符・役・点数、和了判定、シャンテン。天鳳の和了約2,600万件で検証済みとREADMEに記載 | **点数計算テストの正解データ生成**（最有力オラクル） |
| riichienv-core（RiichiEnv） | Rust（`wasm` feature） | Apache-2.0 | 4人/3人、東風/東南、天鳳・雀魂ルールプリセット、点数、和了判定、待ち、mjai対応 | 対局進行のクロスチェック／将来WASMで高速化する際の候補 |
| riichi-tools-rs | Rust（WASM向け） | MIT | シャンテン計算（ルックアップテーブル不要でバイナリが小さい） | WASM版シャンテン計算の候補 |
| riichi-ts | TypeScript | 要確認 | 手牌・役計算 | ✕（作者が非推奨化、未修正の誤りあり） |

**方針**：仕様 §6-3（牌の個体ID管理）や §3-1（局面スナップショット）を厳密に満たすには、データ構造を自分で握れる **TypeScript 自前実装** が向いている。正確性は Python `mahjong` で生成した大量のテストケースと照合して担保する（仕様 §10 の要求に直結）。

## 4. Evaluator（③）の段階的な実装案

| 段階 | 評価内容 | 手法 | 精度表示 |
|---|---|---|---|
| E1 | シャンテン数・受け入れ枚数・有効牌 | 厳密計算 | 確定値 |
| E2 | 和了率・打点期待値（自分の手のみ） | 山の残り枚数から**モンテカルロ・シミュレーション**（Mac：多め／iPhone：少なめ） | 試行回数と信頼区間を表示 |
| E3 | 放銃リスク | 現物・スジ・壁・リーチ者の捨て牌からヒューリスティック推定 | 「暫定評価」ラベル |
| E4 | 押し引き・順位期待値 | E2×E3 と点数状況を組み合わせた期待値比較 | 「暫定評価」ラベル |
| E5（将来） | 総合評価 | 自前学習モデル等を ONNX Runtime Web で差し込み | エンジンバージョンを記録 |

- 評価点（100点満点）は**最善候補との期待値差を相対変換**して算出（§3-3）。
- Mac/iPhone の差は**試行回数の違いだけ**にし、ロジックは共通にする（§4-3「品質が極端に変わらない」）。
- 評価結果には必ず `engineVersion`・`confidence`・`elapsedMs` を付けて保存（§3-4）。

## 6. 実装状況（2026-11-05 時点）

- `src/engine/rules/tile.ts`：牌モデル（種類と個体IDの分離、赤5、牌姿記法）
- `src/engine/rules/shanten.ts`：一般形・七対子・国士のシャンテン数
- `src/engine/rules/efficiency.ts`：受け入れ枚数・打牌候補比較（E1）
- Python `mahjong` と **11,800件** のゴールデン照合で全件一致（`npm run golden:shanten` で再生成）
- 速度（Mac / Node、`npm run bench`）：

  | 処理 | 高速化前 | 高速化後 |
  |---|---|---|
  | シャンテン数（キャッシュ温まり後） | 14.6µs | 2.0µs |
  | シャンテン数（初回・キャッシュなし） | — | 3.8µs |
  | 14枚の全打牌候補比較 | 2.2ms | 0.14ms |

  方式：色（萬・筒・索・字）ごとに「面子数ごとの最大搭子数」を計算してメモ化し、色同士は足し算で合成する。
  キャッシュの上限は1色14枚以内の牌姿の数で決まるので、際限なく増えることはない。
  正しさは Python 照合（11,800件）と、旧・全探索版との突き合わせ（ランダム30,000件）で確認。
  ※ 以前の「0.18ms/手」はウォームアップなしの計測で、実力より遅く出ていた。
  ※ iPhone 実機での計測は未実施。

### 追加（和了判定・点数計算）
- `agari.ts`：和了判定・面子分解・待ち牌 ／ `yaku.ts`：役定義 ／ `score.ts`：役・符・点数・支払い
- Python `mahjong` 2.1.0 と **10,000件** のゴールデン照合（翻・符・役・支払い・積み棒・供託）で全件一致。全役が照合に含まれる（`npm run golden:score` で再生成）
